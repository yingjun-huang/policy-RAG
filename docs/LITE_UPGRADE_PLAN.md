# Policy-RAG 轻量升级方案（知识库和评测集保持不动）

## 1. 先说结论

- **规模不是主要矛盾。** 参考项目 `Adaptive-rag-main/knowledge/` 每篇只有约 400~500B，`rag_eval.jsonl` 约 8.6KB；我们是 32 篇、114 个 chunk、145 + 35 条评测，已经比它丰富。面试官很少因为语料只有几十篇就否定一个项目，他们会追问的是：**为什么这样设计、怎么证明有效、代价是什么**。
- **"包装"和"造假"的区别，正好就是"追问能过"和"追问会露怯"的区别。**

| 可以放心包装（追问也能接住） | 不要写（一追问就露怯，而且属于造假） |
|---|---|
| 选最有利的角度，写最强、但真实的那个数字 | 写代码里不存在的能力，比如把手写的边说成"自动构建" |
| 把规模小说成刻意的设计选择，比如"高密度规则语料，不上 Neo4j" | 写没跑过的指标，比如离线假 LLM 下的 F1 100% |
| 把 bad case 驱动的迭代讲成一个工程故事 | 用最弱的基线来放大提升幅度 |
| 用准确但高级的术语，比如"领域先验规则图"代替"手写邻接表" | 写不知道怎么回答的术语 |

**核心策略：不改语料、不改评测集，花 1~2 天让代码追上简历。** 下面 6 项改动成本都很低，改完之后简历上每个说法都站得住，还能多出几个真实的提升数字。

---

## 2. 六项高性价比改动（每项 Agent 0.5 天以内）

### A. 把"门控"做成真的（解决 `reranker.py` 强制留名额的问题）
- 现在 `clause_graph.py` 里的关键词 cue 表是照着评测题写的，有过拟合嫌疑；`reranker.py` 是无条件把图扩展结果塞进 Top-5。
- **改法**：
  1. 删掉 cue 表的触发逻辑，改为：图扩展候选只有在 Cross-Encoder 分数 ≥ τ 时才保留名额，否则按正常分数参与排序。
  2. τ 在 145 条上做一次扫描（例如 0.0~0.9），输出"效果与延迟随 τ 变化"的曲线，选拐点。
  3. 旧逻辑作为一组对照方案保留在消融实验里。
- **面试收益**：门控有了明确的阈值，还有一张取舍曲线可以讲（P@1 和 Complete@5 之间的权衡）。

### B. 规则图配置化（把"手写"讲成一种设计）
- 把 `_build_edges` 里写死的边挪到 `config/policy_graph.yaml`，例如 `- {src_group: category_rules, tgt: jd_rule_01, type: INHERITS_GENERAL}`，代码只负责加载和校验。
- 再加一个 50 行左右的辅助功能：用正则从正文里抽取"按《…》执行""参照…"这类显式引用，输出**候选边建议**（`scripts/suggest_edges.py`）。
- **面试说法**："冷启动阶段，用专家先验定义了三类边，以配置的形式维护。业务方新增一个品类只需要改 YAML，不用改代码。我也评估过用 LLM 抽边，但几十篇规则文档用 LLM 抽边的噪声大于收益，所以只做了引用正则来辅助发现新边。"这段话真实、有取舍，追问也接得住。

### C. 用真实 LLM 跑一次端到端评测（风险最大的一项，成本最低）
- 运行 `runner.py --mode e2e --live-llm`（DeepSeek，大约 180 个问题 × 4~6 次调用）。
- 新增一个 LLM-judge（可以用 deepseek-reasoner），对照现成的 `gold_answer` 判答案正确性，并统计：
  - Faithfulness 触发率、纠正前后的正确率；
  - 拒答准确率、澄清准确率（数据集里已经有 25 条 clarify、13 条 abstain、11 条 refuse）。
- 拿到的大概率是 85~95% 这类有瑕疵的数字，**这比 100% 更可信**。

### D. 补上端到端延迟和成本
- 跑 C 的同时，按路由（direct/single/multi）记录端到端 P50/P95、首 token 时间（TTFT）、LLM 调用次数和 token 数。
- 简历写"多跳路由端到端 P95 X 秒"，被问到"那 0.89 秒是什么"时，可以说清楚那是检索加重排阶段的耗时。

### E. 重排提速（顺手拿一个真实的优化数字）
- 现在 Cross-Encoder 是检索阶段的瓶颈：报告中 scheme 4→5 从 20ms 涨到 773ms。
- **改法**：只重排 RRF 的 Top-N（N 取 10/15/20 扫一遍），并检查 `providers/cross_encoder.py` 是否已经批量推理。
- **结果**：得到"重排 P95 从 773ms 降到 Xms，Complete@5 损失 ≤ Y"，这是一个真实的工程优化故事。

### F. 准备 bad case 文档（零代码）
- 把 `根目录 UPGRADE_PLAN.md` 里那 11 个 bad case 整理成 `docs/BAD_CASES.md`：现象 → 根因 → 方案 → 改后效果 → 仍然失败的 case 及原因。
- 面试中最加分的就是讲清楚"一个 bad case 怎么一步步修好的"。

## 3. 改写后的简历（包装到位，每一句都能被追问）

> **电商售后政策智能问答系统｜Adaptive & Graph-Enhanced RAG**
> 技术栈：Python、FastAPI、LangGraph、DeepSeek、BGE、BM25、Cross-Encoder、Qdrant、NetworkX、SSE
>
> **项目概述**：面向退换货、运费责任、保修咨询场景，针对"品类特例与通用总则混用""跨文档隐式依赖漏检""过期规则误引"三类典型错误，构建带版本时效控制和规则依赖补全的自适应 RAG 系统。
>
> - **结构化索引与时效过滤**：Markdown 按标题做父子分块，表格整块保留，超长表格按行切分并重复表头；解析生效区间、适用事件、品类写入 Qdrant payload 做前置过滤，**归档规则误召回率从 26.7% 降到 0**。
> - **规则依赖图与门控重排**：通过 bad case 分析发现"细则命中但上位总则语义不相似"的漏检模式，抽象出"细则→总则 / 争议举证 / 互补服务"三类边，用 NetworkX 维护规则依赖图（配置化管理），做 1-Hop 补全；图扩展候选按 Cross-Encoder 阈值门控入选，再按"特例优于总则"的效力顺序组织上下文。在 145 条评测集上，相比 Hybrid+Rerank 基线，复杂问题完整证据覆盖率从 **89.7% 提升到 [B 改后实测]%**，P@1 保持 [ ]%。
> - **自适应流程**：基于 LangGraph 实现 直答/单跳/多跳/拒答 路由，复合问题拆成子查询，按证据充分性最多补检 2 轮，没有新证据就提前停止；关键条件缺失时生成澄清追问，**澄清准确率 [C]%**。
> - **幻觉抑制**：生成后做 Faithfulness 校验和自纠错，接入 DeepSeek 做端到端评测，**答案正确率 [C]%**，纠错触发率 [ ]%，**拒答准确率 [ ]%**。
> - **工程交付**：FastAPI + SSE 流式推送节点状态和答案，分阶段埋点；重排候选截断后 **重排 P95 从 773ms 降到 [E]ms**；多跳路由端到端 P95 [D]s。

和原版相比，主要改了这几处：
- 删掉所有 100%（版本过滤那项改成"误召回率 26.7%→0"，同样亮眼而且真实）；
- 基线换成最强的无图方案；
- "条款拓扑图谱"改成"规则依赖图"；
- 不再写"五路路由"；
- 去掉报告文件名；
- 换上 4 个真实测出来的数字。

## 4. 面试追问应对（提前背熟）

| 追问 | 回答要点 |
|---|---|
| 只有 32 篇文档？ | 售后政策本来就是高密度、强约束的规则文本，难点在规则之间的冲突和时效，不在规模。所以刻意没上 Neo4j 和 GraphRAG 社区摘要，避免过度设计。 |
| 图是怎么建的？ | 冷启动阶段用专家先验定义三类边，配置化维护，并用引用正则辅助发现新边。（方案 B） |
| 会不会对评测集过拟合？ | 边是按类型泛化定义的：INHERITS_GENERAL 覆盖全部 14 个品类，不只是失败的那几个；门控阈值通过扫描曲线选拐点。也承认样本量有限，下一步计划扩大评测集。 |
| 为什么 Hit@3、MRR 略降？ | 图扩展占了一个名额，属于覆盖率和排序之间的取舍。复杂问题需要多份证据，所以优先保证覆盖率。（方案 A 的曲线） |
| 端到端多慢、多贵？ | 拿方案 D 的数字分路由回答，并说明单跳和直答路由会跳过补检。 |
| Faithfulness 判错了怎么办？ | 回答误纠率和人工抽查的情况（自己看 20 条，10 分钟就够）。 |
| 和 Adaptive-RAG 原版的区别？ | 领域相关的三件事：时效过滤、规则依赖补全、效力优先级。 |
